3 运行时进程树

真正跑起来的进程与谁拉起谁。依据：paseo plugin ls（running）+ 日志里的 [paseo] Loading plugin / Plugin ready、server/hooks.ts 的注入器、server/status.ts 的 gh 探测。

ASCII 版
Paseo 宿主 daemon（node）
├─ 插件服务端进程   index.server.ts（paseo plugin ls → running）
│  ├─ gh   每次调用一个短命子进程，20s 超时
│  ├─ git  默认 20s（读出 5s / push 180s）
│  └─ glab
├─ 每个 agent 会话 → MCP 子进程（stdio）
│  └─ node server/mcp/main.ts --workspace <dir>（hooks 注入，alwaysLoad）
└─ 客户端：Paseo App 加载 index.client.tsx（与插件同包，另一个运行时）
插件不监听端口；没有队列 worker、没有定时器进程（见视图 5）。

4 端到端数据流

一次「打开任务板」从点击到列表出现，每一跳的协议。依据 client/deck/BoardView.tsx、server/rpc/issues.ts、server/tracker/targets.ts、server/tracker/backend.ts、server/tracker/github.ts。

ASCII 版
点击 → BoardView(useQuery) → useRpc(issuesListRpc) → 宿主 RPC 通道 → listIssuesHandler
     → resolveWorkspaceTargets（对每个仓库跑 git remote get-url；容器工作区往下找一层）
     → resolveBackend
          ├─ github → gh api graphql（HTTPS 443，20s 超时，凭据由 gh 管）
          ├─ gitlab → glab api（写前查权限 ≥ Reporter）
          └─ local  → readBoard(.deck)、.scratch 同形状也读（不联网）
     → 归一成一份票面，readiness 统一在这里算
     → 回程同一通道 → useQuery 缓存 → 列表 + 计数页签
失败不抛异常：TargetFailure { reason, detail }，顶栏显示真实原因。

5 事件接入与分流

外部事件只有宿主回调这一种入口；没有 webhook、没有队列、没有 cron。有两处 setInterval——设备码授权轮询（server/auth.ts:279）与面板刷新心跳（client/deck/panel/usePanelRefresh.tsx:116），都不是后台业务作业。依据 server/hooks.ts。

ASCII 版
宿主事件（唯一入口，server/hooks.ts）
├─ before("agent.create")
│   ├─ 有 GitHub/GitLab 远端 → 一定注入 MCP（alwaysLoad，只读工具进 preapproved）
│   ├─ 本地后端 → 只有 .deck/ 或 .scratch/ 已存在，或设置里选了 local 才注入
│   └─ 任何异常 → 记 warn，请求原样放行（不拦用户开会话）
└─ on("agent.turn_ended")
    ├─ 无 parentAgentId → 直接 return（不处理主会话）
    └─ 有 → reportEnabledFor(cwd) → TurnReporter.report → 写回父会话 + .deck/handoffs
没有 webhook、没有队列、没有 cron。
两处 setInterval 是「设备码授权轮询」与「面板刷新心跳」，不是后台业务作业。

最核心的写链路：发一条评论。重点是「失败之后到底能不能重试」。依据 server/tracker/write.ts、server/tracker/gh-error.ts、server/rpc/issues.ts。

 ├──────────────▶│                          │                   │                 │
 │               │ resolveWritableBackend   │                   │                 │
 │               │（GitLab 先查权限≥Reporter）│                  │                 │
 │               ├─────────────────────────▶│                   │                 │
 │               │                          │ gh api POST       │                 │

本地后端不经过 gh：postLocalComment 直接写 .deck 下的 Markdown。

7 状态机

这张票「能不能接」的唯一口径：server/tracker/readiness.ts 的 readinessOf()。四态互斥，界面与 MCP 都不许另写一份判断。

ASCII 版
        被指派             关闭/合并
 ready ────────▶ claimed ──────────▶ closed
   ▲   ◀────────                    ▲
   │   全部解除指派                  │
   │ 新增阻塞者          关闭/合并    │
   └──────▶ blocked ────────────────┘
              ◀────── 阻塞者全关
判定顺序（readiness.ts）：closed（state=CLOSED 或 PR merged）→ blocked（任一阻塞者仍 OPEN）
→ claimed（assignees 非空）→ 才是 ready。四态互斥；ready+claimed+blocked = open。

8 部署拓扑

没有容器、没有反向代理、没有域名、没有数据库。所谓「部署」就是把插件目录交给 Paseo。依据 paseo-plugin.json、.github/workflows/ci.yml、package.json。

ASCII 版
开发机 / 服务器
├─ 插件目录 /www/wwwroot/game.kxhyapp.com/paseo-matt-skills-deck
├─ Paseo 运行时（paseo ≥0.13.0 <0.14.0；宿主托管插件进程）
├─ 认证来源：gh 自己的登录态（插件不存 token）
├─ 本地数据（无数据库）
│   ├─ <工作区>/.deck/ · <工作区>/.claude/skills · .agents/skills
│   └─ <PASEO_HOME 或 ~/.paseo>/matt-skills-deck/sites.json（0600）
└─ 出网：api.github.com（gh）· GitLab 实例（glab）

CI：GitHub Actions（.github/workflows/ci.yml）→ node 22 → npm ci → typecheck → test
发布：git tag v*；更新检查 git ls-remote --tags，网络被挡时回落 gh
没有 Dockerfile / compose / pm2 / nginx / k8s：部署 = 把目录交给 Paseo。

9 故障降级关系

谁挂了会影响谁、有没有兜底。全部来自代码里的分支：server/tracker/write.ts、server/auth.ts、server/update.ts、server/tracker/backend.ts、server/hooks.ts。

ASCII 版
gh 没登录        → 面板内设备码流程（token 只走 stdin）→ 轮询到登录成功
写请求 4xx(≠408) → 明确被拒 → 回落 gh issue comment 再试一次
5xx/超时/断连    → 可能已写入 → 不回落、不自动重发 → 报「先刷新确认」
GitLab 权限不定   → 归档/关票/<Reporter → 拒绝写，不赌
git ls-remote 超时 → 回落 gh 查 tag（只放行 api.github.com 的机器）
多仓库没 repoKey   → 拒绝猜，要求指明仓库
MCP 注入失败      → 记 warn，请求原样放行（开会话不被插件拦住）
子会话回传失败     → 记日志；回传件仍在 .deck/handoffs/
插件卸载          → disposeGithubAuth() 收掉等待授权的 gh 子进程

原则：能确定「没发生」才重试；不能确定的，报「可能已发生」让人先确认。
