# 多项目工作区怎么用

一个工作区里放了好几个项目时，插件要知道三件事：有哪些项目、它们各自有哪些模块、这些项目算不算一套。这份文档说清三件事分别怎么配、怎么跑、出了分歧怎么办。

单项目仓库不需要读这篇：什么都不用配，行为与以前完全一样（见最后一节）。

## 1. 配置文件：`.paseo-deck.json` v2

文件放在工作区根目录。v1 只有一个 `repoDir`（选了一个仓库）；v2 是一份项目清单：

```json
{
  "version": 2,
  "projects": [
    {
      "key": "api",
      "dir": "mall-api",
      "repo": "943545721/mall-api",
      "owner": "backend",
      "areas": ["api", "auth", "job"]
    },
    {
      "key": "admin-web",
      "dir": "apps/admin-web",
      "repo": "943545721/mall-admin-web",
      "owner": "frontend",
      "areas": ["orders", "users"],
      "skillsMode": "unified"
    },
    {
      "key": "miniapp",
      "dir": "miniapp",
      "owner": "miniapp"
    }
  ],
  "coordination": {
    "shape": "container",
    "note": "前端 + 后端 + 小程序是同一套产品"
  }
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `key` | 是 | 项目标识。小写字母或数字开头，只含小写字母、数字、连字符，最长 64。作标签与菜单的稳定键，**改它等于换了一个项目** |
| `dir` | 是 | 相对工作区根目录的路径。可以多段（`apps/admin-web`），不许 `/` 开头、不许 `..`、不许反斜杠 |
| `repo` | 否 | `owner/name`（GitLab 可以是 `group/sub/name`）。目录里有可读远端时以远端为准，这里只是补位 |
| `owner` | 否 | 角色，只认 `backend` / `frontend` / `miniapp` / `license` / `ops` |
| `areas` | 否 | 模块键数组。由项目梳理技能产出、人确认后写进来；可以空着 |
| `deprecatedAreas` | 否 | 已废弃的模块键。同步标签时**不建**这些 area 标签，也从不去仓库里删已有的——删了就没人知道它曾经存在，而旧票还挂着 |
| `skillsMode` | 否 | 这个项目的技能模式：`unified` / `per-project`。不写就跟随工作区设置 |
| `coordination.shape` | 否 | 人对「这些项目算不算一套」的声明：`single` / `container` / `mixed`。写了就不再被提示 |

**v1 文件照旧能读**：读出来是一个只有单个项目的清单，插件不会把它改写成 v2。想升到 v2 就自己写（项目梳理技能的报告可以直接照着抄）。

配置写坏时不会静默变成「0 张票」：检查页会按原因点名——目录不存在、不是 git 仓库、没有远端、`key` 非法、字段缺失、JSON 坏了。

## 2. area / role 从哪来

**没有内置清单。** 每个项目结构不一样，而且一直在变，写死一份键表只会越用越偏。area 与 role 由**项目梳理技能**（`/project-survey`）当场读出来：

1. 技能读 `package.json`、`composer.json`、workspace 配置、目录树、`Dockerfile`、CI；
2. 每一项候选都带依据（`路径:行号` 或目录），读不出来的写「未确认」；
3. 重跑只报差异：新增、消失（标「可能已废弃」，不删）、改名嫌疑；
4. 报告交给人确认，**确认之后**才写进 `projects[].areas` 与 `owner`。

确认后这些键会变成标签：`area:<key>` 与 `role:<owner>`，配合十个标准标签一起同步到各仓库。

## 3. 跨仓库依赖

「后端改完前端才能动」这种关系写在子票正文的固定行里：

```text
Blocked by: 943545721/mall-api#42
Blocked by: api#42
```

- 完整写法 `owner/repo#12`，简写 `key#12`（`key` 必须是配置里的项目键）；
- 多个依赖用逗号写在同一行，插件只维护这一行，重复调用不会叠加；
- 本仓库内的依赖仍走原生的 blockedBy 关系，不进正文；
- 读取时会解析这一行，与原生关系**合并**后计算阻塞状态：对方关票后这里的票自动变可接；
- 对方票读不到（仓库不可达、票号不存在）时标「引用失效」，**不算已解除**阻塞。

## 4. 地图：每个项目一张

不做跨项目聚合页。每个项目在自己的仓库里有一张地图，正文按本项目的模块（area）分组，生成骨架时就把分组摆好；跨项目关系只写「怎么引用」，不写别人的票。

## 5. 技能：统一模式与各自模式

技能装到 `<项目>/.claude/skills` 与 `<项目>/.agents/skills` 两处，有两种模式：

| 模式 | 做什么 | 什么时候用 |
|---|---|---|
| `per-project`（默认） | 只补缺失的技能；冲突不覆盖、不删任何文件 | 各项目自己会改技能 |
| `unified` | 先把整份技能**备份**，再清空那两个目录，最后装插件那一份 | 要求所有项目用同一套技能 |

统一模式的顺序是刻意固定的：**备份成功才清空**。备份失败就停手，那个项目一个文件都不动，并在结果里写明原因，其它项目继续。

备份位置：

```text
<工作区>/.deck/backups/skills/<项目 key>/<时间戳>/
  .claude/skills/…      清理前的全部内容（含子项目自己写的技能与 references）
  .agents/skills/…
```

还原就是把这些目录拷回原处：

```bash
cp -a .deck/backups/skills/api/2026-10-30T12-00-00/.claude/skills/. api/.claude/skills/
cp -a .deck/backups/skills/api/2026-10-30T12-00-00/.agents/skills/. api/.agents/skills/
```

两种模式的「全部更新」不一样：`unified` 覆盖写；`per-project` 仍然不覆盖冲突，冲突逐条列出来由人决定。

## 6. 插件怎么判断这是哪种工作区

打开一个目录时，插件先判断形态，判据写出来给人看，不靠猜：

| 形态 | 判据 | 插件做什么 |
|---|---|---|
| 单项目 | 根目录自己是仓库；或子目录只有一个仓库 | 什么都不提示 |
| 多项目容器 | 配置里列了多个项目；或子目录里多个仓库同属一个 owner；或仓库名有共同前缀 | 提示「这是多项目，建议先跑一遍项目梳理」，给一个可复制的提示词 |
| 不成套 | 多个仓库分属不同 owner、名字也没有共同前缀 | 先问怎么处理，列出三条去处 |

不成套时的三条去处：

1. 只把其中几个项目纳入本工作区；
2. 拆成两个工作区，各自一个容器；
3. 全部纳入，但每张票标出来源项目。

三条都不会自动执行。判定结果在检查页可见；觉得判断不对，点「不再提示」会把结果写进 `coordination.shape`，之后不再提醒——插件只记下这个声明，不改项目清单。

## 7. 单项目仓库：什么都不用做

- 没有 `.paseo-deck.json`，或还是 v1（只有 `repoDir`）：行为与以前完全一样；
- 不会出现「项目条」「项目必选」「多项目提示」；
- 技能安装默认 `per-project`，只补缺失，不覆盖、不删；
- 建票、看板、地图都是原来的流程。
