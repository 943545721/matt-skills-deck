matt-skills-deck · 需求 → 地图 → 派单 → 回传

六张图回答一件事：谁在哪一步动手，插件在哪一步只是配置。断网可看，单文件，无外部依赖。

1 三种票：需求、地图、子票是三个东西

需求票是「要什么」，地图票是「怎么走到」，子票是「这一步谁来做」。需求不会自动变成地图——中间隔着一次确认。

ASCII 版
需求票 (requirement)                 地图票 (wayfinder:map)                 子票 (wayfinder:task 等)
┌ 六节正文 ────────────┐            ┌ Destination ─────────┐              ┌ 归属：挂在地图下 ─────┐
│ 问题                 │  确认后    │ Notes                │   拆票       │ 顺序：Blocked by #N   │
│ 目标与非目标         ├──建图─────▶│ Decisions so far     ├──一张票─────▶│ 类型：research /      │
│ 约束 / 备选方案      │            │ Not yet specified    │   一条任务    │       prototype /     │
│ 建议 / 待定问题      │            │ Out of scope         │              │       grilling / task │
└──────────────────────┘            └──────────────────────┘              └───────────────────────┘
 标签：requirement                   标签：wayfinder:map                   三个关系彼此独立：
                                                                           归属 / 顺序 / 类型

为什么需求不等于地图

  • 需求票回答「要什么」，写完它工作区里还没有任何路线——它可能根本不需要拆。
  • 地图票回答「到目的地的路线有几段」，是确认之后才建的容器；正文五块里第一块就是 Destination。
  • 子票才是派单对象：一次 deck_dispatch_plan 的每条 task 对应一张子票。
  • 代码里的口径：shared/requirement.ts 只说「需求票统一带 requirement：不抢 wayfinder 路线标签，路线仍由地图显式挂」。

2 谁触发什么：选窗口不等于派单

这张表是这次疑问的正面答案——「派单窗口」只是署名与路由的默认值，它自己不触发任何动作。

ASCII 版
动作                 谁        入口                              结果 / 边界
选「派单窗口」       人        面板·编排·角色                    只写配置：署名/路由/配额，不派单
建需求票             人        面板·新建票→需求                  一张 requirement 票（六节骨架）
确认需求 / 建地图    人+agent  复制 /wayfinder 提示词 + MCP      地图票 + 首批路线票
派单（算计划）       agent     MCP deck_dispatch_plan            出 providerSpec + prompt + 拒绝清单
真正建子会话         agent     宿主 create_agent                 子会话挂宿主下，带 deck 子会话标
记「谁接手」         agent     MCP deck_issue_report             写本机台账（时间线的会话行）
回传结果             插件      子会话 turn_ended 钩子            handoff 落盘 + 发给父窗口

一句话：绑定派单窗口 ≠ 派单；派单 = 会话里的 agent 调工具 + 宿主建会话。

4 派单闸门：一份配置，六种拒绝，一条层数链

所有拦截都发生在「算计划」这一步，且拒绝时一定说清是哪一条——不夹到上限硬派，也不悄悄降档。

ASCII 版
输入 tasks[{key, prompt, difficulty, map?}] + map + depth + dispatchId
        │
        ▼ 读 .deck/orchestration.json
   读不出 → settings-unreadable      文件坏了 → settings-corrupt（都不许回落默认值派单）
        │
        ▼ 逐条过闸
   empty-prompt · duplicate-key · too-many-children
   depth-exceeded · map-budget-exhausted · route-unavailable
        │
        ├── 拒 → rejected[{key, reason, detail}]
        └── 放 → providerSpec + modeId + labels + idempotencyKey + prompt（抬头 + 正文）

层数：主沟通窗口 0 → 子 1 → 孙 2 → 曾孙 3（maxDepth）
     到上限那层不能派：拒绝，不夹到上限硬派

5 回传链：子会话结束后结果往哪走

插件在这里只做三件事：落盘、去重、找一个还活着的窗口。找不到就是改送，不改写结论。

ASCII 版
子会话 turn 结束
   │ agent.turn_ended（带 outcome）
   ▼
TurnReporter
   ├ reportOnFinish = false → 跳过（记 disabled）
   ├ 按 turnId 去重：同一轮只报一次
   ├ 发给父窗口
   │    父窗口已归档 / 发送失败 → 改送主沟通窗口，回执标 rerouted: true
   │                                两条都失败 → 记 warn，不静默丢
   └ handoff 文件留在 .deck/handoffs/（父窗口收尾时读得到）
