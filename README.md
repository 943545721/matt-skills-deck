# MattSkillsDeck for Paseo

把 [dsh-mattpocock-skills-deck](https://github.com/FeatherHunter/dsh-mattpocock-skills-deck) 移植成 Paseo 插件：
31 个中英双语工程技能（Matt Pocock 那套 + 架构图纸 + 项目梳理），加上多后端工作票面、地图与一组给 Agent 用的 `deck_*` 工具。

当前状态：**DSH 版 A1–A26 已逐项落地**（P0–P19 代码侧完成，P19 为八线全量吸收；仓库公开在 GitHub，打了 `v0.1.0` / `v0.1.1`，可用 git 源安装）。
26 项里 13 项完全对齐、7 项已有但换了出口、2 项以最近等价面承载、4 项部分、0 项未做；逐项证据与剩余差异见
[`docs/port-diff.md`](docs/port-diff.md)，阶段记录见 `PROGRESS.md`。按 D6 决定**不提交公开注册表**。

## 能做什么

- **任务板**：列出工作区所指仓库的 issue，按「地图票优先、开着优先」排序；六个视图（全部、Open、可接、阻塞、
  已关闭、已合并）把可接 / 阻塞 / 已关闭的计数直接写在页签上，另有四种排序；显示最近更新时间、额度读数与
  REST 回退提示，按设置自动刷新；**子票折叠挂在父票下面**（左侧 ▾/▸ 与张数，可一键全部收起 /
  展开），层数不设人为上限（需求 → 地图 → 子票 各缩进一级），父子只按服务端给的归属认，
  父票被筛掉时子票照旧单独占一行；拉取请求独立页签，打开 / 已关闭 /
  已合并三态，只读。
- **仓库详情**：顶栏说明连的是哪个宿主、哪个仓库，并给出描述、可见性、主语言、Star / Fork、打开的票（含 PR）、
  默认分支、最近推送、许可、创建时间与主题；本地 `.deck` 后端则给出目录与票 / 标签的实际数量。详情单独取数并
  缓存 5 分钟，不跟着列表轮询烧额度。
- **容器目录**：工作区本身不是 git 仓库、但直接子目录里有仓库时，任务板把**这些仓库的票合成一块板**：
  每张票带仓库徽标，筛选条可以只看某一个仓库，新建票可选目标仓库，标签页也先选仓库再读改；打开票面能看到所属仓库与本地代码目录，
  复制给 Agent 的提示词也带上仓库键与代码路径。工作区根的 `.paseo-deck.json` 只记「默认看哪个仓库」
  （只存一个单层目录名，建议加进 `.gitignore`），不再缩小板子的范围；票面、标签、地图与 MCP 工具共用
  同一份仓库解析结果。只扫一层，不递归进 `node_modules` 之类的目录。
- **票面**：正文 Markdown、评论、整体替换标签、接手 / 完成（真实写入）、打开远端、复制链接与五种动作提示词；
  **时间线**把建票、每条评论、关票、会话接手与最近变动并成一列（远端给关票时刻，本地后端没有就不写这一行）；
  新建票可勾「地图」；**缺陷**票按实际 / 期望 / 复现 / 环境四段建，缺项会尝试标 `needs-info`、未诊断标 `needs-triage`；
  新建**需求**可选探索 / 实施两种六节模板，自动带 `requirement` 标签，建完可复制 `/wayfinder` 或 `/grill-with-docs` 提示词。
- **会话与工作路线**：输入框胶囊按 agent、页头按 workspace 显示本地台账里的当前票 / 最近动作，
  读不到时如实标「不可读」；胶囊 / 页头 / 助手面板里的 `SessionSheet` 可以把动作提示词填进当前会话或新建会话的输入框，
  由你检查后自己按发送；新建会话在创建时带规则标题，已有会话不能改名。可导出 AI 交接。
- **地图**：`wayfinder:map` 票会多一个「打开地图」入口，一屏给出目标、已定决策、雾、路线、层级与每层进度、
  子票分组（可接 / 认领 / 阻塞 / 关闭），以及可复制的下一步建议。
  **需求票与地图票之间有一条引用边**：建图时带 `sourceIssue` 就在地图正文写一行 `Derived from: #19`
  （GitHub 没有「衍生自」这种原生关系），边只存在这一处，需求票上不另存一份。
  地图页顶部有一行「来自需求 #19」，数据走 `deck.map` 的 `derivedFrom`（`deck_map_snapshot` 同样带这一位），
  点一下回到那张需求票面。
  任务板把这条引用当父子边用：**需求展开就是它建出的地图，地图展开是它自己的子票**，
  缩进与折叠跟其他父子关系完全一样，不再另做一行标签。这一跳不加读——正文那一行本来就在板上。
- **技能**：31 个技能中英双语随包分发，可看原文、可复制原文，按工作区一键安装到 `.claude/skills` 与 `.agents/skills`；
  安装前先列出要写的文件，不自动写入。矩阵页一行一个项目、一格一个客户端目录，**项目清单也能在这里直接编辑**
  （增删项目、改每个项目的技能模式，或把扫到的仓库一键补进来）：保存前逐行校验、旧文件先备份、
  写完按读路径解析回来核对；两个窗口同时改，后保存的那个会被指纹拦下并提示重读。
- **Agent 工具**：20 个 MCP 工具（DSH 九颗冻结工具 + 评论、标签、PR、`deck_next_steps`、`deck_probe`、`deck_handoff`、
  `deck_handoff_to_dispatcher`、`deck_dispatch_plan`、`deck_requirement_dispatch`、`deck_staff_request`、`suggest_next_steps` 十一个扩展）。
  13 个预授权工具（只读工具，加上 `deck_handoff`、`deck_handoff_to_dispatcher`、`deck_staff_request` 三个只写本地旁路件的），
  其余七个改票面的写工具每次都要人确认；GitHub / GitLab / 本地 Markdown 三种后端共用同一套工具。
  合板工作区里，读工具可带 `repo`（`owner/name`）只看一个仓库，省略则覆盖全部；写工具在多仓库下必须
  指明 `repo`——票号只在仓库内唯一，插件不会替你猜。
- **编排**：一个工作区一套派单规则，落在 `.deck/orchestration.json`——指定主沟通窗口、需求窗口与派单窗口、层数上限、
  单次最多派几个；**地图并发预算**（一张地图同一时刻最多几个子会话）也在这一份里，派单时按宿主上
  「已经开着几个」硬拦，超了逐条拒绝并说清还剩几个；给每个客户端注入 `env`（只显示掩码）、追加模型、存「provider + 模型 + 模式 + 思考档位」档案。
  卡片上的「N 个密钥」本身可以点开：它读宿主配置文件，列出源文件路径、匹配的 provider 条目
  （Codex 站点启用时生效的是派生条目 `deck-codex`，会标出来）、每条 provider 的顶层字段名与 env 键名 / 掩码值，
  主地址与已配置模型名原样，地址自身带 userinfo 或凭据类查询参数时同样掩码，
  用来看清「地址 + 凭据 + 其它」各占几条。弹窗里可以勾选要清理的 env 键或整条条目
  （非空或字段格式异常的条目也可确认整条删除，会一起删掉模型 / command / 其它字段）。
  删键时先摘掉条目，再在同一补丁写回保留内容并读回核对
  （未选中的模型清单、追加模型条目及其说明 / 默认项 / 思考档位少一样就报失败）；整条删除只摘掉，读回确认条目已移除；地址 / 凭据键要二次确认。
  整条删除的记录落在 `<PASEO_HOME>/matt-skills-deck-state.json`，自动接管与模型镜像会跳过用户删除的 Codex 条目。
  在卡片重新保存 Codex 配置或启用 Codex 站点后，只有读回确认本次写入和应保留的内容均已落地，才清除删除记录并恢复自动维护；
  写入失败、部分落地或无法核对时保留删除记录。删除记录损坏或不可读时，自动接管、重复 env 清理和模型镜像暂停，状态页会说明原因；清除记录失败也会显示告警。
  客户端卡片上还能给每个模型配一个默认思考档位：派单时档案 / 路由里显式设的档位优先，没设才用这个默认档，
  两处都没有就不传、由宿主用模型自己的默认；模型从卡片清单里删掉后，它上面的默认档不再生效。
  Claude 保存获取到的模型清单或 `ANTHROPIC_MODEL` 时，接口报告的上下文窗口会同步到 `CLAUDE_CODE_MAX_CONTEXT_TOKENS`
  （当前模型优先，没报时取已配置模型的最小窗口），让自动压缩按接口窗口触发；一个窗口都没有时不新增也不删用户写的值。
  接口报过的窗口还会按工作区缓存到 `.deck/model-windows.json`（只存 provider、接口地址、模型 id 与窗口，不存凭据）：
  宿主保存模型时会裁掉 `contextWindowMaxTokens`，之后保存模型、重建 Codex 模型目录、以及重载后卡片上的「接口报 N」
  都从这份缓存补窗口；接口地址换了就不套旧窗口，缓存里没有的模型不编窗口，Codex 目录里的原生模型名照旧保留。
  换地址时上一接口写下的 `CLAUDE_CODE_MAX_CONTEXT_TOKENS` 与 Codex 启动命令里的旧模型目录也会一并去掉（结果里会说明），
  免得新地址继续按旧上限压缩；在新地址上重新获取模型并保存后会自动接上。
  已开着的会话不会重读 env，必须保存后新开会话。
  Codex 的接入地址与凭证写在派生 provider `deck-codex`（继承内建 Codex）上——写在内建 `codex` 上的那份
  宿主根本不读，这也是「配了却不生效」的由来；写入时带地址（或启用站点那一步）才把这条派生条目建出来
  （带 `extends` / `label`，内建条目的模型清单照搬），新建的 `codex/model` 会话随之路由到它。
  只改模型或凭证而没配地址时，仍旧写回内建 `codex`：一条没有地址的派生条目会让之后每张 Codex 会话被拦下。
  派生条目的 env **只写适配器真读的两个键**（`OPENAI_BASE_URL`、`OPENAI_API_KEY`）：别的键写进去没人读，
  只会在客户端卡片上多出几行看不懂的东西。旧版本整份照抄留下的残渣（同一把钥匙的旧键名，如 `SUB2API_API_KEY`）
  由插件在读到客户端配置时顺手清掉——宿主的 provider 补丁是深合并、删不掉单个 env 键，所以走
  「`removeProviders` 整条摘掉 + 同一补丁写回干净形状」（宿主先移除后合并，没有空窗）；只删**值完全相同**
  的重复项，值不一样就当另一套凭证，一个字不动；条目停用时也不动。
  判据统一成「派生条目可用」（继承 codex + 没停用 + 有地址），写、读、建会话三处同一套；地址键名只接受
  `OPENAI_BASE_URL`（适配器写死的），写成 `sub2api_base_url` 之类会被直接拒绝而不是静默无效。
  显示名仍留在内建 `codex` 上，因为卡片上的名字取自宿主快照那一条；在 **Paseo 自己的 provider 设置**
  里停用这条派生 provider 就等于回到宿主原生 Codex（插件客户端页不列这一行，所以那里没有开关）。
  模型清单要写成**两份**：宿主的模型选择器是按 provider 条目各显示一份的——「Codex」那行读内建条目，
  注入真正生效的 `deck-codex` 是另一行，所以只写一份的后果是「这个窗口能选那个模型、换个项目的新窗口就没有了」。
  保存模型时同一条清单两边都写（各自落在条目自己用的那把键上：`models` 是替换内置列表、`additionalModels` 是追加，
  搬到另一把等于写了个不生效的地方）；用户在面板里取消的模型两行一起消失，但内建那一行上用户自己在 Paseo
  设置里加的模型留着（面板读的是派生条目，那些模型在面板上看不见，删掉就是替人做决定）；
  读客户端页时若两份对不齐，以可用的派生条目为准**只补不删**地照写一次
  （用户可能在 Paseo 自己的设置里给内建那一行加过模型，读一次面板就把它们抹掉是替人做决定），
  用户不必为了「换个窗口也能看到」再保存一遍。对齐失败只给一句提示，不挡读状态——它影响的是别的窗口看到什么，不影响会话。
  内建 `codex` 上还留着旧地址、`deck-codex` 又根本不存在时，插件自己把那条地址搬过去（env 只搬适配器真读的
  两个键，地址尾部斜杠归一，凭证补成适配器真读的 `OPENAI_API_KEY`，模型清单一起带过去，并顺手把内建条目上那条地址清掉）。
  这条清理**只是顺手**：宿主对 provider 补丁是深合并还是整块替换、能不能删掉已写的键，目前没有确凿结论
  （`PROGRESS.md` 里两条记录相反），所以删不掉也正常——地址留在内建条目上宿主照样不读，真正管用的是
  下面那条告警。读客户端页与新建 Codex 会话两条路都会触发，
  搬完就是「卡片上看到的 = 会话真正用的」，不需要用户再去建一条站点；同一条地址每次运行只试一次，
  宿主不收派生 provider 时只告警、不反复写盘（第二次起照样返回失败原因，不假装没事）；用户在客户端页
  重新保存地址会让这条判定作废、再试一次。先存凭证、后存地址也没关系：建派生条目时会把内建条目上的那把
  凭证一起带过去（地址不抄旧的，那是这次写入自己决定的）。往派生条目里写地址
  而调用方没说停用时，顺手写 `enabled: true`：用户存了地址就是要它生效，残条目的 `enabled: false` 不能跟着留下。
  写完读回不是一条能用的派生条目（继承 codex / 地址 / 启用任缺一样）就直接报失败，不报「保存成功」——
  否则用户会在「保存成功」和「建不了会话」之间来回打转。
  派生条目已在但被停用/没地址时，插件不擅自翻用户的开关，改为在客户端页顶部告警「这条地址现在不生效」，
  重新保存一次地址就写回去并启用。搬不动（或派生条目被用户停用）才拒绝创建并把地址写进报错
  （读不到宿主配置时同样拒绝——这一条对**所有** Codex 创建生效，不区分工作区与有没有站点，daemon
  抖动窗口内 Codex 会话会整体建不出来，非 Codex 客户端不受影响——不说「配了没生效」），免得悄悄用 `~/.codex/config.toml` 里的
  旧地址开会话；没配过地址的普通 Codex 会话不受影响。客户端卡片主区只留接入地址、凭据、模型与站点（可选备用线路），
  名称与 id 收进「高级」——那是核对配置、改名字时才看的东西。
  客户端页只列插件真能为它注入接入地址的两家 **Claude / Codex**：其余客户端（OpenCode、Copilot、Cursor、Pi 等）
  在宿主里没有读 `*_BASE_URL` 的路径（OpenCode 只有前缀约定，没有实证），配进去的地址与凭证不会被任何会话用上，
  所以客户端列表与模型选择器里
  都不出现（它们在 Paseo 自己的界面里照常可用）。隐藏了哪些不逐条告警——宿主动辄报出七八家，那会变成页面顶部
  常驻的噪音；口径写在客户端页页头那一行说明里。这两家之外的建站与改配置在后端一并拒绝（直接调 RPC 也一样，
  免得 agent 绕过界面写一份没人读的配置），早先留下的站点记录仍可删除。真会白存的才单独告警：被隐藏的客户端或派生 provider `deck-codex`
  下还存着站点、宿主报出来的全是不支持的家（这时列表为空，得说清是「都不支持」而不是「宿主没报」）、
  以及某一档派单规则或客户端档案指向了不支持的客户端（会话能建，但接入地址与凭证注入不了）。
  改完接入地址或模型后，客户端页的「刷新宿主模型」让宿主立刻重读按工作区缓存的清单（不重启 App，也不动在跑的会话）；
  按 trivial / normal / hard / critical 四档难度指定客户端与模型（没配的档借用 `normal` 的路由，连 normal 也空着才用内置默认目标，
  借用这件事在页面上和 `deck_dispatch_plan` 的 `routeFrom` / `warnings` 里都写出来，不悄悄换成别的档）。
  派单时 `deck_dispatch_plan` 给出该用的客户端、标签与抬头（`depth` 必须自己报，超层直接拒绝，
  标签里的父会话按真实调用者写）；**每条放行的任务还要落一张票**——票上标着难度
  （`difficulty:hard`）与执行客户端（`client:codex`），正文写明派单窗口、层级、模型与地图。
  自动派单（`deck.orchestration.dispatch`）先建票再建会话，票建不出来就不派这条；会话标签
  `deck.ticket=#票号` 是「从会话反查票」的唯一硬链接，抬头里也写着票号。
  `deck_dispatch_plan` 本身只读，它把票的标题 / 正文 / 标签一起给出来，由调用方用
  `deck_issue_create` 建（这一步要人确认），建完把 `deck.ticket` 换成真票号再 `create_agent`。
  票闸不走 MCP 也挡得住常见写法：会话在 shell 里用 `gh` / `glab` 的 `issue` 写动作、写票面的 `api` 调用
  （POST / PATCH / PUT / DELETE，或没写方法却带字段时的默认 POST；目标是 issues / labels / milestones / graphql），
  或 `label delete/edit/clone` 时，插件在权限请求上直接拒绝，并回一句
  「走 deck_issue_create / deck_issue_patch / deck_issue_labels」；`bash -c` / `-lc`、`eval`、`$(…)`、子 shell、
  `gh -R owner/repo` 与 `sudo` / `env` / `timeout` 前缀都会钻进去看。只对「有远端仓库，或目录里已有
  `.deck/` / `.scratch/`」的工作区生效；只读的 `gh issue list/view`、显式 GET、`label create` 照常放行
  （`graphql` 只看得出带不带字段，带字段就按写处理）。
  这是按命令文本认形状，不是沙箱：`curl` 直连 API、`gh alias` 别名、`echo … | bash` 这种把脚本从标准输入
  喂给 shell 的写法，以及不带 shell 详情的客户端窗口认不出来；底线仍是不给会话 GitHub 写凭证。
  难度不是算出来的：由派单方显式声明（缺省 `normal`），或从票面标签 `difficulty:*` 读出，不让模型自评。
  子会话用 `deck_handoff` 写回结果（只写自己名下那份；没有 `PASEO_AGENT_ID` 就失败，这类缺身份的窗口会在编排页的
  会话树顶部给出提示：有几个窗口、最近被哪个工具拒过。Codex 会话就是这样——本机实测
  它的 MCP 子进程不继承会话环境，重开也一样；收尾仍会按最后一段输出回传），
  收尾时插件把它回传给创建它的窗口，一层一层往回走；
  另外给**进度窗口**抄一份更短的【进度】（谁、哪张票、结论）——进度只汇总在进度窗口，
  主窗口不再收每条回传的副本，要看结论去派单窗口或进度窗口；
  目标窗口正在跑活时消息先排队，等它这一轮结束再送，不把消息插进正在进行的回合；
  卡在「等人点确认」的窗口也算忙（硬塞会清掉它的确认框），归档或关掉的窗口则直接丢掉队列；
  子会话的权限确认（写文件、跑命令、提问、切模式）只弹在它自己窗口，等满 45 秒还没人点，插件会往主沟通窗口递一句
  【等你确认】，写明是哪一支、在等哪种确认（写文件带路径，shell 只说种类、不回显命令）——否则会话就那么卡着，
  连回合结束的回传都不会有；会话被归档或关掉就撤掉提醒；
  上一级那个窗口已经归档发不进去时改送主沟通窗口并在正文里写明绕道，页签里的会话树显示这条链路。
  这条链由插件强制执行，不靠身份提示词：**入口门**只认绑定的**派单窗口**——主窗口调派单被拒并提示改用
  `deck_handoff_to_dispatcher`，需求窗口、进度窗口与其他会话同样被拒，面板人工派单（不带会话身份）放行并在回执里说明是人工操作；
  **需求窗口**是唯一被允许写需求票的会话：绑定了它之后，其他会话经 MCP 建 / 改需求票（`deck_issue_create` /
  `deck_issue_patch` / `deck_issue_labels`）会被拒；它自己也只写需求票，不建工作票（地图与路线票同样算工作票）、不改文件、不派活；
  还没绑定需求窗口时这道闸不拦，避免老工作区被锁死。票闸已经把 `gh` 建票全局拦住；主窗口与进度窗口经 MCP 建票同样被拒，
  `deck_map_plan_create` 建出的地图与路线票也走同一道闸；执行会话不受影响；
  **交接工具** `deck_handoff_to_dispatcher` 只收主窗口的「需求票号 + 任务 + 验收」，写成
  `.deck/dispatch-handoffs/pending/` 的交接件，不建票、不建会话、不碰 `gh`，同一份内容重复交只算一次；写件时没有绑定的
  派单窗口就直接拒绝，写完之后窗口忙、解绑或换人都留在队列里，等当前绑定空下来再送，送成功才移到 `sent/`，
  连续五次送不出去移进 `failed/` 并记日志；
  **创建门**在主窗口 / 需求窗口 / 进度窗口直接开出子会话时当场归档并通知父窗口（派单窗口、执行会话、角色窗口本身、无父会话都放行）；
  **执行门**拒绝主窗口 / 需求窗口 / 派单窗口 / 进度窗口的 `write`、`edit` 与会改文件的 shell（重定向、`tee`、`rm`/`mv`/`cp`、
  `sed -i`、`git commit/checkout/...`、装包与构建命令等），读、搜、跑测试与 MCP 工具照常，`gh` / `glab` 让给票闸只拒一次；
  执行窗口本来就要改文件，不受这道闸影响。读不出编排文件或分不清会话属于哪片时，创建门与执行门都放行并记 warn——
  这是护栏，不是沙箱。
  RPC 派单与 MCP 同一口径：每条任务必须挂需求票，没票（`no-requirement`）、读不出需求标签（`requirement-unreadable`）、
  还没 `deck:定稿`（`requirement-not-finalized`）都逐条拒绝，不进计划也不占并发名额；链条上票建不出来仍是 `ticket-failed`。
  面板派单表单的票号同样必填，没填当场拦住，不用等一个来回。
  `deck:` 前缀的私标签只能由面板按钮增减：`deck_issue_create` 建票、`deck_issue_labels` 整体换标签、
  `deck_issue_patch` 的 `addLabels` / `removeLabels` 四条路都拒（能悄悄补上定稿就等于绕过按钮那次核，
  能悄悄撤掉定稿就等于先摘标签再改成派单必拒的样子）；面板补定稿标签时服务端还会按**此刻**的正文
  与工作区仓库清单重算一次影响面，按钮读到的是缓存也不影响结论。
  票面写坏不必等到派单才发现：`deck_issue_create` 建票时、`deck_issue_patch` **显式整段换正文**时，
  正文里只要出现「## 影响面」，就当场按表校验表头、分隔行与列数（已经定稿的票再按定稿口径整张核一遍：
  数据行、结论、核的人），写坏就拒绝、一个字节都不落盘（只追加进度 / 备注 / 阻塞的调用不动这一节，所以不核）；
  派单仍因票面被拒（`bad-impact` / `missing-impact` / `empty-impact` / `unknown-workspace`）时，
  不论拒绝发生在 MCP 派单窗口还是面板的「按区派单」，插件都把原因写成一张**条子**放进 `.deck/window-notes/pending/`，relay 在该工作区下一次会话回合结束时
  （或需求窗口建出来时）按当时的绑定投进需求窗口——用户不用再复制粘贴转述。拒绝的 detail 只说条子去了哪：
  「已排进队列」「同样的原因还排着队 / 已送过 / 之前投递失败过」，不把「已入队」说成「已送达」。
  需求窗口还没绑定时条子留在队列里等绑定；绑了但那一会儿不在线时按次重试（两次之间至少隔一分钟，免得几秒就把次数烧光），累计 5 次没送成才移进 `failed/`
  并记一行日志——一次送不到就丢，等于让人再也不会知道票坏在哪。
  注入 `env` 时会把该客户端已有的键一起提交——宿主落盘是整块替换，只交新键会把别的键冲掉。
  这套流程（需求票 / 地图票 / 子票怎么分工、每步是谁在动手、闸门与回传链）画成了一张离线图纸：
  [`docs/dispatch-flow.html`](docs/dispatch-flow.html)，六张图 + 每张的 ASCII 版。
  面板上有两条人工派单入口：编排页的**派单台**按「先建票、再建会话」派一条任务（中间不经过模型）；
  定稿需求票上的**按区派单**第一次点只出清单，第二次才建票建会话。两条都走 RPC，和 MCP 共用同一套票门与预算闸。
  归档是宿主的软删除：记录与客户端那边的对话都还在，只是不再出现在默认列表里，而宿主**没有**取消归档的接口。
  面板的「已归档」页签把本工作区已归档的会话连同 provider 会话 id 一起列出来（可按 id / 标题筛），
  并为每条拼好 `paseo import <会话 id> --provider <客户端> --cwd <目录>`，复制即用；
  没有会话 id 的记录会明写原因，不给半条命令。宿主的归档是跨全部工作区的，一次读不完时
  页面上有「读取更早的」继续往前，警告里写明这一趟读了多少条、是否还没读完。
- **多项目工作区**：`.paseo-deck.json` 可以写成 v2 项目清单（`version` / `projects[]` / `coordination`），
  也可以直接在面板的技能矩阵页里编辑这份清单（增删项目、改 `skillsMode`、把扫到的仓库补进来），不用退出面板手改文件；
  每个项目有自己的目录、仓库、角色（后端 / 前端 / 小程序 / 授权 / 运维）与模块清单（area）；
  任务板多出一条项目条，按项目显示开 / 闭 / 可接 / 阻塞，筛选条能按 area 与角色叠着筛；
  跨仓库依赖在正文写固定一行 `Blocked by: 项目键#12`（也认 `owner/repo#12`），读的时候合成一条边，
  对方仓库读不到就标「引用失效」而不是当成已解决；地图页把这类引用单列并给出对方票的状态与外链。
  标签页按清单补齐 `area:*` / `role:*`；诊断页可按项目补齐 `.github/ISSUE_TEMPLATE` 四类模板（只补缺失，绝不覆盖）。
  v1 的 `{"repoDir": "..."}` 照旧能读，插件不替你改写成 v2。细则见 [`docs/multi-project-workspace.md`](docs/multi-project-workspace.md)。
- **其他页**：标签配色（读、改、读回核对、复制配色提示词）、版本管理（状态、diff、提交历史、stage / commit / pull / push、AI 交接、git worktree 多工作树一览）、
  诊断（16 项检查目录 + 六步仓库初始化引导 + 日志开关 / 复制 / 清空；修复动作全部接线，认不出的动作明示「未支持」，不放空按钮）、
  插件设置（后端、刷新间隔、调试日志、更新检查）。
- **双语**：界面跟随 App 语言（中/英），标题与按钮在同一套词表里。

## 后端

设置页的「后端」决定票读写落到哪；`auto` 是默认值：

| 后端 | 读 | 写 | 数据位置 / 依赖 |
|---|---|---|---|
| `auto` | 有 GitHub 远端走 GitHub，有 GitLab 远端走 GitLab，都没有走本地 | 跟随实际后端 | — |
| `github` | 是 | 是 | `gh` 已安装并 `gh auth login` |
| `gitlab` | 是（issue 与评论，系统备注过滤） | 是，写前检查当前账号至少 Reporter；失败区分「没写入」与「可能已写入」 | `glab` 已安装并 `glab auth login` |
| `local` | 是 | 是 | 工作区里的 `.deck/`，也识别 `.scratch/`，无外部依赖 |

本地后端的布局：

```
.deck/
  issues/<n>.md            # frontmatter + 正文
  issues/<n>.comments.json # 评论
  labels.json              # 标签目录与颜色
```

`.deck/` 可以直接用编辑器改、用 git 提交、用 grep 找。如果工作区已经是 `.scratch/` 布局，读路径也认它；
两种布局不会自动互搬。切换后端不会自动搬数据，诊断页会提示「切过去会看不见哪些票」；
GitLab 的写权限由每次操作前的闸门判断，至少需要 Reporter。

## 安装

```bash
# 本地目录（开发用）
paseo plugin install /绝对路径/paseo-matt-skills-deck

# Git（推荐钉 tag）
paseo plugin install git:943545721/matt-skills-deck --ref v0.1.1

paseo plugin reload matt-skills-deck     # 改完代码热更新
paseo plugin ls                          # 应显示 running
paseo plugin logs matt-skills-deck       # 出问题时看这里
```

前提：Paseo `>=0.13.0 <0.16.0`（0.14 的客户端 SDK 与 0.13 逐字节相同、服务端只多出 `defineAgentTool`
 与几个只读字段；0.15 已逐文件比对过 SDK，旧钩子仍保留为别名，本机在 0.15.4 上实跑通过；0.16 之后没比对过，不放）。GitHub 后端需要 `gh` 并已登录；GitLab 后端需要 `glab` 并已登录，
写操作还要求当前账号在目标项目至少是 Reporter；只用本地后端则不需要任何 CLI。没有登录时，任务板和诊断页会直接给一个「登录 GitHub」按钮：
浏览器流程把 gh 的一次性验证码搬到面板上，连不上 github.com 时改用 Token（只经 stdin 交给 gh，插件不保存）；
不需要自己开终端敲命令。缺什么时面板不装死，会直接说明原因。

插件设置页（Paseo 设置 → 插件 → MattSkillsDeck）可以改后端、刷新间隔、调试日志和像素皮肤
（跟随 Paseo / 深色 / 浅色 / 经典像素），并检查远端有没有更新的 tag。
更新检查只查不装：宿主没有安装插件的调用面，这里给出一条可复制的 `paseo plugin install ...` 命令。

## 结构

```
paseo-plugin.json    清单：id、要求、媒体
index.client.tsx     注册面：工作区面板、整页界面、侧栏行、设置页、胶囊、页头、助手面板、命令中心、时间线
index.server.ts      注册 RPC 与生命周期钩子
shared/              两端共用的 RPC 契约（Zod）：issues、map、repo、labels、env、logs、settings、requirement、update、auth、session、checks、publish
client/deck/         插件界面：任务板、地图、技能、标签、版本、诊断、设置、初始化引导、像素皮肤
client/deck/board/   任务板的项目条与 area / role 筛选（纯计算单独成文件，node 直接可测）
client/deck/skills/  技能页的项目 × 客户端矩阵
client/deck/surfaces/ 原生座位：胶囊、页头、助手面板、命令中心、斜杠命令、附件源、时间线
client/deck/session/  SessionSheet + prefill：填入当前 / 新建会话输入框、复制兜底
client/deck/panel/    助手面板页签（检查目录等）
server/tracker/      票面领域逻辑：多后端分派、gh / glab / 本地 Markdown 读写、地图正文、路线与建议
server/rpc/          RPC 处理器（一条 RPC 一个文件）
server/workspace/    多项目工作区的落盘动作：issue 模板、标签同步的计划与执行
server/mcp/          给 Agent 的 MCP 服务端（协议层 + 20 个工具，含多项目的 repo 作用域）
server/session.ts    会话创建 / 发送 RPC（兼容保留）、技能可用性核实、台账附注
server/ledger.ts     agent / workspace 两个作用域的本地台账
server/checks.ts     16 项检查目录与六步引导
server/publish.ts    发布计划 / dry-run（不执行 git / gh）
server/hooks.ts      before agent.create：按工作区后端注入 deck 工具
server/env.ts        环境检查的逐项规则
server/update.ts     远端 tag 检查
templates/skills/    随包的 31 个技能（中英双语）
```

分层硬规则：`client/` 不 import `node:*`，`server/` 不 import `client/`，跨边界数据一律过 `shared/` 的 Zod 契约。
两套 tsconfig 就是为了让这三条在编译期就报错。

## 与 DSH 版的差异

完整的逐项对照见 [`docs/port-diff.md`](docs/port-diff.md)。最影响使用体感的几条：

- 面板落在**工作区标签页**，不是常驻右栏；输入框胶囊与页头会按 agent / workspace 动态注册，
  但 0.13 没有全局状态栏，KPI 与故障信息仍在面板内。
- 「一键填入输入框」真的填输入框；能填入的入口（胶囊 / 页头 / 助手面板 / 时间线 / 票面 / 地图 / 技能页）
  都走 `SessionSheet`，写宿主草稿 store 并读回校验后导航到已有会话或新建会话，**不发送消息**；
  目标输入框已有草稿时先提示、确认后才覆盖；写不进去就复制提示词，让你自己粘贴。
  你检查文字后自己按发送，复制提示词作为只读出口保留。
  草稿 store 的模块编号不是公开协议，所以按「上次记住的编号 → 已知编号 → 宿主的模块注册表」
  依次找；生产包通常不暴露模块注册表，这时失败横幅上多一个「自动查找草稿 store」按钮，
  点了一次性逐个试探模块（这一步会执行宿主模块，因此不自动做），分片执行、有总时长预算，
  编号范围覆盖到 2 万（实测 0.13.2 的 Web 包里 store 在 3598、0.14.0 在 3601；桌面 App 自带的前端包还可能不同），
  找到就记住编号，下次直接命中。认 store 按形状（`getState().drafts` + 写方法）而不只认
  `useDraftStore` 这个名字，宿主改名也照样能找到。失败时横幅里带着宿主在试过的编号上报的
  原话（含上次记住的那个编号），以及全量试探跑了多少个编号——便于判断是加载器不对、
  编号变了还是注册表没暴露。
- Agent 工具走**独立 MCP 子进程**；GitHub / GitLab 远端一定注入，本地后端只在工作区已有 `.deck/`
  （或在设置里明确选了 local）时注入，避免每个空目录都多出十几个工具。写工具默认要确认。
- 会话自动命名只做到**创建时规则标题**：`agent.create` 能看到调用方给的 title，但没有改名 API，
  已存在的会话不能重命名，也不做模型摘要。
- GitLab 后端**读写都有**，每次写前检查权限（至少 Reporter）；本地 Markdown 后端也读写，
  默认 `.deck/`，并识别 `.scratch/`。
- 发布有两条路线：检查页向导走 `deck.publish.run` 真建仓推送，`deck.publish.plan` / `confirm` 是只出计划的 dry-run 路线；
  检查页里 `wizard / form / setupRun / ensureLabels / glabAuthLogin` 这些动作还没接线，界面会明说。
- 像素风的基础来自 DSH 原版 `PixelStyles.ts`：直角、等宽粗体、墨底纸字票号、红边故障横幅；
  「经典像素」完整保留原版 3px 框、硬投影、8px 棋盘与棕 / 米色板。
  深色 / 浅色两套改成**细线 + 页签**：卡片和分隔线只画 1px，普通控件不再带投影，
  导航与筛选是「选中项下划线」而不是一排彩色方框，一屏里只有一个主按钮是实心强调色。
  深色按同一套几何做深底浅字（像 IDE 的 dark theme），整块底取 Paseo 深色界面实测的
  `#181b1a`，强调色统一为暖金；浅色是**纯白底 + 浅灰描边 + 单一蓝色强调**，同样不铺棋盘；
  默认跟随 Paseo，面板顶栏有一键深 / 浅快捷键，设置里也可以选「经典像素」。
  原版是 DOM + CSS，Paseo 面板是 React Native，所以 CSS 类名不能 import，颜色与几何则逐项对齐
  （`client/deck/pixelTokens.ts` + `tests/pixel.test.mjs` 逐值钉住）。

## 已知限制

- 本机验证只到「编译 / 单测 / reload / 失败分支」；真实 GitHub / GitLab 读写与 MCP 注入需要在有登录态的环境里跑一遍。
  GitLab 写路径目前只用假 `glab` 验过命令与失败分类，没有在真实 GitLab 项目上留过写入。
- Agent 工具要求 daemon 跑在 Node 22.18+（插件直接用当前 Node 跑 `server/mcp/main.ts`）。版本不满足或入口文件缺失时，
  插件会跳过注入并在 `paseo plugin logs` 里说明，不会挂一个起不来的服务。
- MCP 服务名固定 `matt-skills-deck`（预授权名单按服务名映射），不要在工作区里自建同名服务。
- 像素风外观没有截图验证：这个环境起不了 Paseo 桌面端窗口。
- GitLab 的合并请求（MR）还没接；PR 页签只对 GitHub 后端返回数据。
  发布 RPC 只生成 argv / dry-run，没有执行段，也还没有发布页面。
- 版本页没有 `git worktree list`，多工作树同时开工时只能看当前工作树。
- 更新检查需要本机有 `git` 且能访问 GitHub；失败时如实报错，不会猜一个「已是最新」。
- 插件 API 处于实验期，`requirements.paseo` 钉在 `>=0.13.0 <0.16.0`：0.13 / 0.14 / 0.15 的 SDK 都比对过，
  0.14 的**守护进程**（不只是 App）没实跑过；0.15.4 的守护进程本机实跑通过。0.16 之后没比对过，不放。
