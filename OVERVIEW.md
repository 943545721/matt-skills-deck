MattSkillsDeck brings Matt Pocock's engineering skill set and an issue board into Paseo.

It bundles 31 skills for planning, triage, implementation, review, handoff, surveying a project's own modules and drawing an architecture map, each in English and Chinese, and adds a workspace panel for the issues of the repository that workspace points at. The board header says which host and repository the workspace points at, with the repository's description, visibility, main language, stars, forks, open count, default branch, last push, license and topics; a local `.deck` board shows its directory and ticket / label counts instead. If the workspace is a container directory rather than a repository, the board looks one level down and merges the issues of every repository it finds into one board: each ticket carries its repository badge and local code directory, the filter row can narrow to one repository, new issues pick their target repository, and the label page asks which repository first. A selection stored in `.paseo-deck.json` at the workspace root only sets the default view, not the board's scope; MCP tools take an optional `repo` argument and refuse to guess when several repositories are present. The board shows ready / blocked / closed counts on the view tabs, filters and sorting, freshness and rate-limit readings, and pull requests on their own tab. It opens one issue with its body, comments and blockers, and can comment, create an issue, a four-field bug report or a requirement, place the matching skill prompt in the input of an existing or new chat, replace labels, take an issue or close it. Issues labelled `wayfinder:map` open a map page that reads the map body's five sections, groups tickets into ready / claimed / blocked / closed, layers them by blocking edges with per-layer progress, and suggests next steps you can copy as a prompt. A composer pill follows each agent and a header button follows each workspace, showing the local work route; prompts can be placed in the current session's or a new one's chat input for review before sending. A `.paseo-deck.json` file can list several projects — each with its own directory, repository, role and module list — and the board then grows a project strip with per-project open / ready / blocked counts, while filters narrow by module and role; cross-repository dependencies written as one fixed body line turn into real blocking edges, an unreadable target is reported as stale rather than resolved, and the label page plus the diagnostics page can fill in `area:*` / `role:*` labels and each repository's issue templates, never overwriting a file that already exists. The diagnostics page runs sixteen checks with a six-step setup guide and names the repair actions it cannot perform instead of showing dead buttons.

Skills are copied into a workspace from the panel's skills page. Nothing is written into the repository until you press install, and the page lists the files it will create before it does.

New agent sessions get twenty MCP tools through a small MCP server the plugin starts for them. Reading context, listing issues, reading one issue, reading a map, reading next steps, listing pull requests, probing the environment, previewing a dispatch, previewing a requirement split and suggesting next steps are preapproved; so are `deck_handoff`, `deck_handoff_to_dispatcher` and `deck_staff_request` — they only write the sub-agent's own report file or local queue files, and without them an unattended dispatch breaks at the last step; commenting, creating or patching issues, relabelling, reporting bugs, linking tickets and creating map plans ask for approval first. GitHub and GitLab remotes always get tools; the local backend gets them once the workspace has a `.deck/` board (or the settings say `local`).

The backend is chosen in the plugin settings: GitHub via `gh`, GitLab via `glab` with each write gated on at least Reporter permission, or a local Markdown board under `.deck/` (it also reads an existing `.scratch/` layout). The plugin never stores a token; GitHub and GitLab data goes only to those remotes. The daemon machine needs the chosen CLI installed and signed in; the local backend needs none. When GitHub is not signed in, the board and the diagnostics page offer an in-panel sign-in: the browser flow shows gh's one-time code on the panel, and a token flow covers machines that cannot reach github.com (the token goes to gh over stdin and is never stored by the plugin). The plugin requires Paseo 0.13.

The panel follows the app's language, in Chinese or English. The plugin runs on the daemon with the daemon user's permissions, like any other plugin, and runs `git`, `gh` and `glab` only inside the workspace it belongs to.

A new **Orchestrate** tab decides how one workspace splits a requirement across windows. Roles name the discussion window (where you talk), the requirement window (the only one allowed to file requirement tickets) and the dispatch window (which hands work out), plus the depth cap, how many children one dispatch may create, and **per-map concurrency budgets** (how many sub-agents may work on one map at once; a dispatch over the cap is refused task by task, with the running count in the detail). Clients lets you inject `env` into each provider (keys and base urls, shown masked), add extra models, and save named profiles of provider + model + mode + thinking option. Each model on a client card can also carry a default thinking level: dispatch prefers a level set explicitly on a profile or route, falls back to that model default when there is none, and sends no level when neither exists (the host then uses the model's own default); a default stops applying once its model is removed from the card's list. Saving fetched Claude models or `ANTHROPIC_MODEL` also syncs the reported context window to `CLAUDE_CODE_MAX_CONTEXT_TOKENS` (preferring the current model, then the smallest configured window); without a reported window, the plugin neither adds nor removes that env value. Reported windows are also cached per workspace in `.deck/model-windows.json` (provider, endpoint, model ids and windows only — never credentials), because the host drops `contextWindowMaxTokens` when it saves models: later model saves, Codex catalog rebuilds, and the card's reported-window reading after a reload all take the window from that cache, while a changed endpoint does not inherit old windows and a model with no cached window gets none invented; switching endpoints also drops the previous endpoint's `CLAUDE_CODE_MAX_CONTEXT_TOKENS` and its Codex catalog flag, with a warning, until models are fetched and saved again; native Codex model names stay in the catalog. Already-open sessions do not reload env, so the change requires a new session. Routing maps trivial / normal / hard / critical to a profile or a concrete client and model; a difficulty with no route of its own borrows the `normal` route (the built-in default target when even normal is empty), and both the row and the dispatch result (`routeFrom` / `warnings`) say so instead of quietly swapping the difficulty. All of it lives in the workspace's `.deck/orchestration.json`. When work is dispatched, `deck_dispatch_plan` tells the child which client to use, which labels to carry (including the host's `paseo.parent-agent-id`, written with the actual caller) and what preamble to send; `depth` is required and a level past the cap is refused outright. The child records its result with `deck_handoff` — always under its own id, and the call fails when that id is unavailable (such windows are flagged at the top of the Tree section with a count and the last refused tool (Codex sessions land here, and reopening does not help)) — and when its turn ends the plugin reports it up to the window that created it, so results climb one layer at a time (if that window is gone, the report goes to the designated discussion window and says it was rerouted) — the **Tree** section shows that chain by indentation. The chain is enforced by the plugin, not by the role prompts: only the bound dispatch window may call `deck_dispatch_plan` or `deck_requirement_dispatch` (the main window is refused and pointed at `deck_handoff_to_dispatcher`; the requirement window, the progress window and any other session are refused too, while a panel dispatch with no caller identity is allowed with a warning). The main window hands work over with `deck_handoff_to_dispatcher`, which writes an outbox item under `.deck/dispatch-handoffs/` and never files a ticket or creates a session; a child session opened directly by the main, requirement or progress window is archived on creation and its parent is told; the requirement window files tickets with `deck_issue_create` / `deck_issue_patch` / `deck_issue_labels` (never work tickets, maps and route tickets included) and, once one is bound, every other session's write to a requirement ticket is refused, including adding the `requirement` label to a work ticket (an unbound workspace stays ungated so it is not locked out); the main and progress windows are refused when they try to file tickets through MCP — maps and route tickets from `deck_map_plan_create` go through the same gate — while execution windows are unaffected; and write / edit / file-mutating shell requests from the main, requirement, dispatch and progress windows are denied, while reads, searches, tests and MCP tools still pass — execution windows are unaffected. When the config cannot be read or a session's workspace cannot be pinned down, the creation and execution gates allow and log a warning: this is a guard rail, not a sandbox. Every dispatch path also requires a requirement ticket; a missing ticket, an unreadable one, or one without `deck:定稿` is refused per task before it enters the plan. A broken impact table no longer waits for dispatch to show up: `deck_issue_create` and an explicit whole-body `deck_issue_patch` parse the section whenever the body carries it and refuse a bad header, separator or column count without writing a byte (a finalized ticket is checked in full — rows, conclusions, reviewers — so it cannot drift out of the state the finalize button accepted; calls that only append progress, notes or blockers leave the section alone and are not checked). The panel's create form and map route tickets go through the same check. `deck:`-prefixed private labels can only be added or removed from the panel: all four MCP paths (creating a ticket, replacing the label set, and `addLabels` / `removeLabels` on a patch) refuse them, since silently adding the finalize label would bypass the button's check and silently dropping it would let a bad body pass as finalized; when the panel adds the finalize label the server re-runs the impact check against the body and repo list as they are right now, so a stale cache cannot decide it. When dispatch is still refused for a ticket fault (`bad-impact`, `missing-impact`, `empty-impact`, `unknown-workspace`), the plugin writes a **note** under `.deck/window-notes/pending/` and a relay delivers it into the requirement window bound at that moment, on the workspace's next session turn (or when that window is created) — so nobody has to copy the message by hand. The refusal only reports where the note went (queued / still queued / already delivered / an earlier delivery failed), never calling a queued note delivered; an unbound window leaves it queued, a bound-but-offline one is retried against that same receiver (never more than once a minute; a newly created or newly bound requirement window gets the note straight away) and only moves to `failed/` with a log line after 5 unsuccessful attempts. The Skills tab can also draft a skill from a requirement: the plugin writes a skeleton with valid frontmatter plus a prompt, you fill the prompt into a session, and the rewritten file is validated (frontmatter fields, description length, whether the body is still the skeleton) before it is installed into `.claude/skills` and `.agents/skills`; a same-named file with different content is a conflict, never an overwrite, and drafting a skeleton never overwrites an existing draft unless you press "reset to skeleton".
Writing `env` resends every key that client already has (the host persists the whole env block, so a single-key patch would wipe the rest), and saving a client profile keeps the host's own `icon` / `color` / `featureValues`; a read-back that comes up short is reported as an error, not as success.
